# Три части лабораторной работы

## 2.1 Git

Отработать ветвление GitFlow командами Git на локальном репозитории. Для лёгкого отдельного задания используется файл с правилами записи в прачечную. Порядок команд приведён в `practice/gitflow-demo.sh`. Запускать скрипт нужно в командной оболочке с поддержкой sh, указав новую папку:

```sh
sh practice/gitflow-demo.sh ../laundry-git-practice
```

Скрипт откажется работать в существующей папке. Он создаёт main и develop, затем feature/booking-rules, release/1.0.0 и hotfix/1.0.1. Для слияний применяется `--no-ff`, чтобы в истории сохранились отдельные узлы. Теги отмечают версии 1.0.0 и 1.0.1. Глобальные настройки Git не меняются.

Для осмысленного выполнения можно открывать скрипт и выполнять команды по очереди, проверяя после каждого этапа `git status` и `git branch`. Расширение git-flow не обязательно: методология реализуется обычными командами Git.

Сохранить скриншоты создания репозитория, коммитов feature, слияний release и hotfix и команды:

```sh
git log --graph --decorate --oneline --all
git tag
```

В основном проекте аналогичный порядок реализован удалённо через ветки и Pull Request. Он не заменяет выполнение локальных команд в части 2.1.

## 2.2 GitHub Desktop

Эту часть выполнить в установленном приложении. Предварительно войти в аккаунт SoftyMaNA.

1. File → Clone repository → URL. Вставить `https://github.com/SoftyMaNA/dorm8-laundry-queue.git`, выбрать новую локальную папку и нажать Clone.
2. В Current repository убедиться, что выбран dorm8-laundry-queue. В History открыть один из коммитов и посмотреть изменённые файлы.
3. Через Current branch переключиться на develop, нажать Fetch origin. Если появилась кнопка Pull origin, получить изменения.
4. Через Branch → New branch создать `feature/desktop-notes` от develop.
5. В локальной папке создать `docs/desktop-observation.md`. Записать две собственные строки: какое действие выполнялось и что показал Desktop.
6. В Changes просмотреть разницу. В Summary указать `docs: добавить наблюдение о GitHub Desktop`, затем нажать Commit to feature/desktop-notes.
7. Нажать Publish branch или Push origin. Открыть репозиторий на GitHub и убедиться, что новый файл виден в этой ветке.
8. Создать Pull Request в develop, проверить Actions, затем выполнить слияние. На исходную main без подготовки версии изменения не направлять.
9. Вернуться в Desktop, выбрать develop, нажать Fetch origin и Pull origin. Проверить, что файл появился в develop.

После этих действий будет подтверждена работа с локальной копией, просмотром изменений, коммитом, отправкой и получением изменений. До выполнения этих шагов нельзя считать часть 2.2 завершённой.

## 2.3 GitHub

В репозитории проверить Code, Issues, Pull requests, Actions и Wiki. Задачи назначены владельцу. В Pull Request видны изменения и результат автоматической проверки. В Actions открыть задание «Четыре теста PHP и MySQL», развернуть каждый из четырёх тестов и скачать артефакт JUnit.

Для отчёта сохранить главную страницу с README, список веток, теги релизов, назначенную задачу, слитый Pull Request, четыре успешных шага Actions и страницы Wiki.

Отдельное требование об организации нельзя заменить личным репозиторием. Пока владелец репозитория - SoftyMaNA, личный аккаунт. Для завершения этого пункта нужно создать бесплатную организацию и согласовать размещение проекта в ней. Не приглашать фиктивных участников. Ссылка на Figma в текущую часть не включается.

## Что объяснить при защите

Git хранит локальную историю, ветки и теги. GitHub хранит удалённую копию и предоставляет Issues, Pull Request, Actions и Wiki. GitHub Desktop является графическим клиентом Git. Коммит фиксирует изменение, push передаёт его на сервер, fetch получает сведения о новых коммитах, pull дополнительно объединяет их с локальной веткой. Тег обозначает конкретную версию.
